# Анатомия качественного теста

Хороший тест падает тогда и только тогда, когда сломано поведение, которое он
описывает, — и по его падению сразу понятно, что именно сломано.

## 1. Arrange — Act — Assert

Тест состоит из трёх частей: подготовить данные, выполнить одно действие,
проверить результат.

```rust
#[test]
fn discount_starts_at_exactly_1000() {
    // Arrange
    let cart = Cart::with_total(1000);
    // Act
    let price = cart.price_with_discount();
    // Assert
    assert_eq!(price, 950);
}
```

Если в тесте несколько «Act», это несколько тестов.

## 2. Одно поведение — один тест, и говорящее имя

Имя отвечает на вопрос «что должно быть правдой?»:
`discount_starts_at_exactly_1000`, `empty_input_returns_error`. Не `test1` и не
`test_discount`. Когда такой тест падает, имя уже объясняет проблему.

## 3. Проверяйте поведение, а не реализацию

Тест проверяет то, что видно снаружи: возвращаемое значение, ошибку,
изменение состояния. Не то, какие приватные функции вызывались. Тогда тест
переживёт рефакторинг и упадёт только при реальной поломке.

## 4. Детерминизм и независимость

- Никакого текущего времени, случайных чисел, сети и порядка выполнения — либо
  фиксируйте их (заданное время, seed), либо выносите за границу теста.
- Тесты не зависят друг от друга и от порядка запуска. Каждый готовит свои данные.

«Мигающий» тест, который иногда падает, хуже отсутствующего: ему перестают верить.

## 5. Точные утверждения

`assert!(result.is_ok())` скажет только «не ок». `assert_eq!(result, Ok(950))`
покажет ожидание и факт. Сравнивайте конкретные значения и добавляйте
сообщение, если по значению неочевидно, что пошло не так.

## 6. Границы и классы эквивалентности

Входные данные делятся на классы, внутри которых поведение одинаковое
(«сумма меньше 1000 — без скидки»). Достаточно одного значения из класса, но
**каждая граница** проверяется с обеих сторон: 999 и 1000, 4999 и 5000.
Большинство ошибок живёт именно на границах: `<` вместо `<=`, ошибка на единицу.

## 7. Регрессионный тест: сначала красный

Нашли ошибку — сначала напишите тест, который её воспроизводит и **падает**.
Только потом исправляйте код. Зелёный прогон после исправления доказывает, что
исправлено именно это, а тест не даст ошибке вернуться.

## Чего избегать

- Логики в тестах (`if`, циклов с вычислением ожидания): тест должен быть
  очевидно правильным.
- Копирования реализации в тест: такой тест повторит ту же ошибку.
- Проверки сразу всего в одном огромном тесте.
- Тестов без утверждений.
