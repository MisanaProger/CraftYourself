# Как запускать тесты и читать вывод

Тесты — самый быстрый способ узнать, что код делает то, что вы думаете. Но
пользы от них мало, если вы не умеете запустить нужную часть и понять, что
именно сломалось.

## Запуск: всё, часть, один тест

Каждая экосистема умеет запускать все тесты сразу и сужать запуск:

| Задача | Rust (cargo) | Python (pytest) | C/C++ (CTest) |
|---|---|---|---|
| Все тесты | `cargo test` | `python -m pytest` | `ctest --test-dir build` |
| Один пакет / модуль | `cargo test -p globset` | `python -m pytest tests/test_parser.py` | `ctest -R parser` |
| По имени теста | `cargo test parse_range` | `python -m pytest -k parse_range` | `ctest -R '^parse_range$'` |
| Показать вывод `println!`/`print` | `cargo test -- --nocapture` | `python -m pytest -s` | `ctest --output-on-failure` |
| Остановиться на первой ошибке | `cargo test -- --test-threads=1` и чтение первой ошибки | `python -m pytest -x` | `ctest --stop-on-failure` |

Фильтр по имени — главный приём при отладке: вы запускаете только тест,
который воспроизводит проблему, и получаете ответ за секунды, а не за минуты.

В Craft Yourself тесты запускаются в **песочнице**: код проекта выполняется в
изолированном контейнере без сети, с ограничениями по памяти и времени, и не
может изменить файлы в вашем рабочем каталоге. Кнопка «Запустить тесты» во
вкладке Tests и команда `est test` делают одно и то же.

## Как читать вывод

Возьмём типичный вывод `cargo test`:

```text
running 3 tests
test tests::parses_simple_range ... ok
test tests::parses_inclusive_range ... FAILED
test tests::rejects_garbage ... ok

failures:

---- tests::parses_inclusive_range stdout ----
thread 'tests::parses_inclusive_range' panicked at src/lib.rs:21:9:
assertion `left == right` failed
  left: [1, 2]
 right: [1, 2, 3]

test result: FAILED. 2 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out
```

Читайте его в таком порядке:

1. **Итоговая строка** (`test result`) — сколько прошло, упало, пропущено.
2. **Имя упавшего теста** — какое поведение сломано.
3. **Место** (`src/lib.rs:21:9`) — строка с проверкой, а не с ошибкой в коде.
4. **Ожидание и факт** — `left` (что получили) и `right` (что ожидали). Именно
   разница между ними — ваша первая подсказка.

Ошибка **компиляции** — не упавший тест: тесты даже не запускались. Сначала
почините сборку.

## Зелёный — ещё не значит «правильно»

Если все тесты прошли, это говорит только о том, что проверено. Тест, который
ничего не утверждает, всегда зелёный. Поэтому полезная привычка — один раз
убедиться, что тест **умеет падать**: временно сломайте код или ожидание и
посмотрите, что тест это заметил.

## Попробуйте

1. Найдите в проекте, как запускаются тесты (вкладка Tests подскажет команду).
2. Запустите все тесты, затем — только один, по имени.
3. Временно поменяйте ожидаемое значение в любом тесте, запустите его и
   прочитайте вывод по схеме выше. Верните значение обратно.
