# Архитектура Craft Yourself

Соответствует архитектурному ТЗ **Developer Edition v0.3**. Модульный монолит
на Rust, Local-first, chat-first интерфейс на React + TypeScript.

## Слои и crates

```
 frontend (React)  ──REST /api/v1 · WS /api/v1/events──►  est-api ◄── est-cli (`est`)
                                                            │
                                                     est-application   ← сценарии + порты (traits)
                                                            │
         ┌────────────┬─────────────┬────────────┬──────────┴──┬──────────────┬─────────────┐
     est-storage   est-git    est-projects  est-workspace   est-ai      (адаптеры портов)
     (SQLite)     (git CLI)   + est-languages (~/.est, IDE) (LLM Gateway)
                                                            │
     чистая логика:  est-ai-policy · est-documentation · est-dependency (ADI) ·
                     est-discipline (ESM) · est-exercises (манифест)
                                                            │
                                     est-domain  →  est-core
```

`est-domain` не зависит от SQLx, Axum, Git, контейнеров или LLM.
`est-application` объявляет порты (`ProjectRepository`, `ConversationRepository`,
`EngagementRepository`, `AdiRepository`, `GitPort`, `LlmProvider`, …);
инфраструктурные crates их реализуют; `est-api::runtime` — composition root.

## Сквозной сценарий (§30)

1. `POST /tasks/{id}/start` — рабочий каталог `~/.est/workspaces/<project>/<task>`,
   ветка `est/<task>`, диалог Issue и **engagement L0**.
2. `POST /conversations/{id}/messages` — Policy Engine до любой модели:
   * вопрос об API → карточка `sources` (исходники, документация), модель не вызывается;
   * запрос выше уровня → `engagement.escalation.proposed` на **одну** ступень, запрос заблокирован;
   * иначе → AI Gateway с системным промптом уровня; превышение лимита кода вырезается.
3. `POST /engagement/escalations/{id}/accept|reject` — согласие поднимает уровень на
   ступень и повторно обрабатывает исходный запрос; отказ — ответ в пределах уровня.
   `POST /conversations/{id}/engagement/raise` — пользователь сам просит следующую ступень.
4. Работа во внешней IDE; EST видит её через Git (`/sessions/{id}`, `/diff?against=base`).
5. `POST /tasks/{id}/complete` — финальный ADI (`scoring_version = observed-0.1`).
6. `/analytics/adi`, `/analytics/disciplines` — независимые ADI и ESM.

## Решения, принятые при реализации

- **Концептуальные вопросы** объясняются на любом уровне (§8.3); уровнем
  ограничена только помощь с решением задачи.
- **Определение требуемого уровня** — детерминированные правила
  (`est-ai-policy/src/engagement.rs`), а не модель: модель не может обойти политику.
- **ADI v0** (`observed-0.1`) считается только по наблюдаемым событиям:
  ответы ИИ по уровням, собственные коммиты, отклонённые эскалации,
  концептуальные вопросы (малый вес). Сама эскалация без использования помощи
  ADI не повышает. Структурированная оценка модели — следующий шаг.
- **Повторное завершение Issue** заменяет её ADI-оценку и ставит её в конец
  порядка (для затухания по числу Issue); равные timestamp упорядочиваются по номеру.
- **Удаление диалога** удаляет сообщения, эскалации, состояние engagement,
  события диалога и ADI задачи; диалог активной Issue удалить нельзя.
- **Локальный daemon** принимает запросы только с собственным `Host` и
  одноимённым `Origin` (защита от DNS rebinding и CSRF).
- **Облачные провайдеры (AI Gateway).** Ученик подключает Claude, ChatGPT,
  Gemini, DeepSeek, Kimi, Qwen, кодинг-планы (Kimi Code, Qwen Coding Plan),
  Ollama или любой OpenAI-совместимый API в «Настройки → Нейросети».
  Список провайдеров — `~/.est/config/providers.toml` (без секретов); выбор
  там важнее `[llm]` из `config.toml`. Активный провайдер лежит в
  `LlmSlot` и переключается без перезапуска; смена пишет событие
  `ai.provider.changed` (имя, модель, endpoint, remote — без ключа).
  Политика не зависит от провайдера: уровень, лимиты и граница документации
  решаются до вызова модели.
- **Ключи, введённые в UI,** хранятся в `~/.est/secrets/llm/<id>.key`
  (каталог 0700, файл 0600) — отдельно от конфигурации, событий, логов и
  экспорта; API только записывает и удаляет ключ и сообщает, есть ли он.
  Переменная окружения из настроек провайдера по-прежнему поддерживается.
  Потребительские подписки (Claude Pro/Max, ChatGPT Plus/Pro, Google AI) не
  дают API-доступа сторонним приложениям и не поддерживаются; «подписка»
  здесь — кодинг-планы, выдающие собственный ключ.

- **Программы по запросу** (`est-application/src/generation.rs`,
  `est-learning/src/generated.rs`). `POST /learning/generated` с темой,
  уровнем и числом уроков (3–10) запускает генерацию в фоне (202): модель
  пишет план, затем каждый урок. Что примет система, решает код: ответ
  разбирается и проверяется (JSON плана и теста, Markdown урока, HTML-документ
  страницы), id уроков и вопросов назначает код, размеры ограничены, вопрос с
  неверным ключом отбрасывается; негодный ответ повторяется один раз с причиной
  отказа, затем генерация завершается ошибкой. Хранится в `generated_programs`
  (миграция 0004) с id `gen-<uuid>` и дальше обслуживается теми же
  `/learning/programs/{id}/…`, что и встроенные; ответы тестов не покидают
  сервер, в экспорт попадают только тема, название и список уроков. Генерация —
  учебный материал, а не помощь по Issue: она не связана с диалогом, не
  меняет уровень engagement и не влияет на ADI. Прерванная перезапуском
  генерация помечается как failed. События `learning.program.generation.*`.
- **Формулы LaTeX** (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`) в Markdown рендерит
  KaTeX: он строит DOM-узлы сам (`katex.render`, без `innerHTML`), с
  `trust: false` и лимитами размера; библиотека грузится при первом
  использовании.
- **HTML5-страницы от модели** — новый вид урока `page` в программах по
  запросу и блоки ```` ```html ```` в ответах ментора. Страница никогда не
  вставляется в DOM приложения: сервер отдаёт её как изолированный документ
  с тем же CSP `sandbox allow-scripts`, что и артефакты
  (`/learning/programs/{id}/lessons/{lesson}/page`,
  `/conversations/{id}/messages/{message}/pages/{n}` — n-й html-блок
  сохранённого ответа ассистента), и добавляет скрипт `est:resize`; интерфейс
  показывает её в `<iframe sandbox="allow-scripts">` и принимает только
  `est:resize`/`est:progress` версии 1. Политика (`est-ai-policy`,
  `ResponseConstraints::max_pages`): страницы в ответах ментора — только с
  уровня L2, для любого вида вопроса: одна страница до 400 строк / 64 КБ вне
  бюджета кода. На L0–L1 страницы нет даже для концептуального вопроса и даже
  короткой: её блок вырезается (`policy.page_removed`), остальной ответ
  сохраняется. Сервер отдаёт только страницы, прошедшие политику
  (`meta.pages` сообщения). Переводы и критерии приёмки страниц не содержат.
  Страницы уроков сгенерированных программ к уровню не привязаны: это учебный
  материал, как встроенные артефакты.
- **Разбор задач** (`est-problems`, `est-application/src/problems.rs`).
  `POST /problems` принимает то, что ученик вставил: ссылку, условие, примеры,
  теги, рейтинг/сложность и язык (Python, C++, Rust). С сайта задачи ничего не
  загружается. `est-problems` (чистый) распознаёт ссылки Codeforces
  (`4A`) и LeetCode (slug), переводит формулы Codeforces `$$$…$$$` в `$…$`,
  ограничивает размеры и описывает практический проект: `PROBLEM.md`,
  шаблон решения и проверку. Задачи stdin/stdout проверяются
  `run_samples.sh` (каждый `samples/NN.in` против `NN.out`, без учёта
  концевых пробелов, таймаут 10 с, итог `est-samples: N passed, M failed`
  разбирает `est-languages`); задачи LeetCode — функции, примеры ученик
  оформляет тестами (`unittest`, `assert`, `cargo test`). Дальше это обычная
  Issue (`TaskType::Algorithm`, `TaskSource::Problem`): L0, согласие на
  эскалацию, песочница с образом языка, ADI при завершении. Системный промпт
  добавляет этапы разбора и что значит каждый уровень для задачи (на L0–L1
  не называть алгоритм) — уровень и лимиты кода по-прежнему решает код.
  Повторный импорт той же задачи на том же языке продолжает её.
- **Рекомендации** (`est-application/src/recommendations.rs`). Снимок
  активности собирает код из наблюдаемых данных: прогресс программ и баллы,
  Issue и задачи со статусами, уровнем помощи, эскалациями, результатами
  песочницы и ADI, практикованные дисциплины. В снимке только агрегаты и
  названия — ни сообщений, ни кода, ни путей; `GET /recommendations/activity`
  показывает его ученику до отправки. `POST /recommendations` — один запрос к
  модели; ответ проверяется: программы и Issue — только по id из снимка
  (названия берутся из данных), ссылки на списки задач Codeforces/LeetCode
  собирает код из очищенных тегов и рейтинга, остальное отбрасывается, не
  больше 6 пунктов. Хранится в `recommendations` (миграция 0005) вместе со
  снимком, попадает в экспорт; на ADI и Skill Matrix не влияет.
- **Сводки сессий и профиль знаний** (`est-domain/src/knowledge.rs`,
  `est-application/src/knowledge.rs`). При завершении или прерывании сессии
  код пишет `SessionSummary` (таблица `session_summaries`, миграция 0006):
  те же наблюдаемые события, что и для ADI (только до момента завершения),
  уровень помощи, тестовые запуски песочницы по порядку, критерии приёмки,
  собственные коммиты и итоговый ADI. В сводке — счётчики, id и название
  задачи, без сообщений и кода. Сигналы (`worked_independently`,
  `heavy_help`, `tests_recovered`, `criteria_open`, `abandoned`, …) выводятся
  фиксированными правилами из счётчиков; «самостоятельно» — завершено без
  ответов выше L1 и без уровня выше L1, «сильная помощь» — ответы L3–L4.
  Профиль знаний считается при запросе из всех сводок по темам: дисциплины ESM,
  теги задачи (темы документации, платформа задачи), тип задачи. Состояние
  темы: `needs_practice` — ничего не завершено, прервано больше, чем
  завершено, или больше половины завершённых — с ответами L3–L4;
  `independent` — не меньше половины завершённых самостоятельно; иначе
  `developing`; уверенность по числу сессий (до 2 — low, до 5 — medium).
  Темы без сессий отсутствуют, а не равны нулю. Сессии, завершённые до
  появления сводок, суммируются при первом запросе (ADI задачи — только её
  последней завершённой сессии). Удаление диалога удаляет сводки его сессий;
  они пересобираются без данных диалога. `GET /sessions/{id}/summary`
  (409 для активной), `GET /knowledge/profile?lang=`; профиль (темы и
  сигналы последних сессий) входит в снимок для рекомендаций, сводки — в
  экспорт. На ADI и Skill Matrix не влияет. Событие `session.summary.created`.
- **Оценка навыков по evidence** (`est-discipline`: `assess`, `matrix`;
  `est-application/src/skills.rs`; каталог `esm-catalog-0.2`). Свидетельства —
  только наблюдаемые результаты: каждая попытка теста (Theory) и улучшение
  результата тренажёра (Practice) хранятся в `lesson_results` (миграция 0007;
  `learning_progress` хранит лишь лучший балл, баллы, записанные раньше,
  учитываются один раз); завершённые практика и Issue берутся из сводок
  сессий: Practice — среднее из последнего тестового прогона (0/100) и доли
  выполненных критериев, если они есть; Diagnosis — 100, если упавшие тесты
  потом прошли; Independence — по наивысшему уровню помощи (L0–L1 → 100,
  L2 → 70, L3 → 40, L4 → 20), только пока диалог не удалён. Чтение, прерванные
  Issue и отсутствие измерения свидетельствами не являются; ADI не входит.
  Навыки урока задаются в `program.toml` (`skills = ["discipline/skill"]`,
  проверяется тестом `est-learning`); без них — свидетельство для дисциплин
  программы целиком; у Issue — для дисциплин задачи; у практики — для навыков
  её урока. Сгенерированные программы пока свидетельств не дают (у них нет
  дисциплин). Правила: учитывается последний результат по каждой паре
  (источник-объект, измерение); балл — среднее с весами (практика и Issue ×2);
  статус: нет данных — `not_assessed`, один объект — `insufficient_evidence`,
  последнему свидетельству больше 180 дней — `needs_reassessment`, от трёх
  объектов из разных источников или измерений — `established`, иначе
  `provisional`; уверенность по числу объектов (1–2, 3–5, 6+). Дисциплина
  оценивается по всем своим свидетельствам; история — 30 последних.
  Оценки дисциплин передаются в снимок для рекомендаций.
- **Потоковые ответы** (`est-ai-policy/src/stream.rs`,
  `est-application/src/streaming.rs`, `est-ai`). `LlmProvider::generate_stream`
  передаёт текст по мере генерации: OpenAI-совместимые API и OpenAI —
  `stream: true` и SSE `choices[0].delta.content` (сервер, ответивший обычным
  JSON, тоже поддерживается), Claude — SSE `content_block_delta`/`text_delta`
  (текстовые блоки соединяются как в обычном ответе; `refusal` и событие
  `error` — ошибка). По умолчанию провайдер отдаёт ответ одним куском.
  Политика проверяет ответ целиком: код и HTML-страницы могут быть удалены из-за
  того, что идёт дальше, а текст вне fenced-блоков не удаляется никогда. Поэтому
  в поток попадает только он: `ProseStream` распознаёт ограждения так же, как
  политика (строка, начинающаяся с ```` ``` ````), придерживает строку, которая
  ещё может стать ограждением, и вместо содержимого блока сообщает
  `withheld`. События `ai.answer.started`, `ai.answer.delta` (`text` или
  `withheld: "code"`, `seq`), `ai.answer.finished`, `ai.answer.failed` с
  `in_reply_to` уходят только в WebSocket и не пишутся в журнал событий: это не
  наблюдения, и на ADI они не влияют. Отправка объединяется (строка, 48 байт или
  60 мс). Сохранённый ответ после проверки политикой
  (`conversation.message.created`) заменяет черновик; интерфейс показывает
  черновик, пока запрос не завершён, и не перезагружает данные на каждую дельту.
- **Внешние действия и их гейты** (`est-ai-policy/src/gates.rs`,
  `est-application/src/remote.rs`, порт `RemoteSources`, адаптер
  `est-remote`). Действий два вида. *Чтение* (Issue и репозиторий с GitHub /
  GitLab, условие задачи с Codeforces / LeetCode) разрешено, только если его
  начал ученик, в запросе есть `allow_network: true` и хост известен
  (`FETCH_HOSTS` и `gitlab_hosts` из `[remote]`); без разрешения — 403 с
  `permission: "network"`, порт не вызывается; разрешение пишется событием
  `permission.network.granted` (хост, цель, адрес). *Публикация* (пока —
  комментарий к Issue, из которой создана задача) двухшаговая:
  `POST /tasks/{id}/issue/comments` только готовит черновик — что, куда, от
  чьего имени — и возвращает digest (FNV-1a от вида, хоста, адреса и текста);
  `POST /publish/drafts/{id}/confirm` с тем же digest в течение 15 минут
  публикует его один раз (черновик удаляется и при неверном digest),
  `DELETE /publish/drafts/{id}` отменяет. Политика отказывает в пустом тексте,
  тексте длиннее 8000 символов и тексте, похожем на ключ или токен (правило 6),
  и предупреждает (`mentor_assisted`), если в диалоге Issue был уровень L3+.
  Черновики хранятся в памяти и после перезапуска пропадают. Ментор (модель)
  не может инициировать ни чтение, ни публикацию: `Initiator::Mentor`
  получает отказ на любом уровне. Токены — только из переменных окружения,
  названных в `[remote]` (`GITHUB_TOKEN`, `GITLAB_TOKEN` по умолчанию); GitHub
  токен также поднимает лимит запросов. События `publish.drafted` (без
  текста — только длина), `publish.completed`, `publish.discarded`. На
  уровень engagement и ADI внешние действия не влияют.
- **Импорт Issue** (`est-issues`). `POST /issues/preview` читает Issue и
  репозиторий и ничего не сохраняет; `POST /issues/import` читает их заново
  (решает сервер, а не то, что показал интерфейс), отказывает непригодной
  Issue, подключает репозиторий (или берёт `project_id`, например форк) и
  создаёт задачу один раз (`TaskSource::Issue`, повторный импорт возвращает
  её же). Пригодность — фиксированные правила, без модели: блокируют
  pull request, закрытая Issue, архивный репозиторий, метки
  duplicate/invalid/wontfix; предупреждают закрытое обсуждение, исполнитель,
  пустое/короткое/очень длинное описание, метки вопроса или обсуждения, 30+
  комментариев, два года без активности, нет лицензии; в пользу Issue —
  метки для новичков и help wanted, чек-лист. Задача: тип и сложность по
  меткам, описание без HTML-комментариев шаблона (до 24 КБ, со ссылкой в
  начале), невыполненные пункты чек-листа — критерии приёмки, дисциплины по
  типу. Дальше — обычная Issue: L0, согласие на эскалацию, ADI. Событие
  `issue.imported`.
- **Подбор Issue и задач** (`est-application/src/discovery.rs`,
  `IssueQuery` в `est-issues`, `est_problems::search`). `POST /discovery`
  с необязательной целью ученика, видами (`issues`, `problems`) и
  `allow_network`. Разрешение на поиск по нужным хостам (api.github.com,
  codeforces.com, leetcode.com) проверяется гейтом **до** вызова модели:
  без него — 403, модель не вызывается. Модель получает цель (как данные),
  тот же снимок активности, что и для рекомендаций, и языки проектов и
  отвечает только планом: до трёх поисков Issue (ключевые слова, язык,
  `beginner`) и до трёх поисков задач (платформа, теги, рейтинг Codeforces
  или сложность LeetCode), каждый с причиной. Код проверяет план: ключевые
  слова очищаются от кавычек, двоеточий и операторов (модель не может
  добавить квалификаторы вроде `repo:`), язык и теги — только из списков,
  рейтинг округляется и становится окном [r−100, r+200]; негодный план
  повторяется один раз. Строку поиска GitHub собирает код (`is:issue
  is:open no:assignee archived:false`, язык, метки для новичков). Поиски:
  GitHub search API; Codeforces `problemset.problems` (с числом решивших);
  LeetCode GraphQL `questionList` (без Premium). Каждый кандидат — из
  результата поиска, ссылок от модели нет; Issue проходят правила
  пригодности (кроме лицензии — её поиск не возвращает, она проверяется при
  импорте) и ранжируются (подходящие, метки для новичков, чек-лист, короткое
  обсуждение, свежесть), до 8; задачи — в окне рейтинга/сложности,
  бесплатные, по популярности, до 4 на поиск и 9 всего; уже импортированные
  Issue и задачи исключаются. Неудавшийся поиск не прерывает остальные и
  попадает в отчёт `searches`. Результат хранится в `discoveries`
  (миграция 0008), попадает в экспорт; `GET /discovery` — последний.
  Событие `discovery.completed` (счётчики, есть ли цель, модель — без текста
  цели). Импорт найденного — обычный импорт (повторное чтение, проверка, L0);
  на уровень, ADI и Skill Matrix подбор не влияет.
- **Загрузка условий задач.** `POST /problems/fetch` возвращает то, что ученик
  иначе вставил бы сам (`ProblemInput`), для проверки в форме; импорт — прежний
  `POST /problems`, с теми же нормализацией и лимитами. Codeforces:
  `contest.standings` даёт название, рейтинг и теги, страница задачи — условие
  и примеры (`est_problems::html`: абзацы, списки, `<pre>`, код, индексы,
  сущности; скрипты и стили отбрасываются, многострочные тесты собираются из
  `test-example-line`). Если страница недоступна (например, защита от ботов),
  возвращаются метаданные и `statement_found: false`. LeetCode: GraphQL
  `question` — название, сложность, темы и HTML условия; примеры
  `Input:/Output:` становятся образцами; Premium-задачу нужно вставить вручную.
  Ответы длиннее 4 МБ не читаются.
- **Совместимость страниц модели** (`est-api/src/routes/isolated.rs`). Модель
  пишет страницу как для обычной вкладки, а в песочнице часть API недоступна.
  Перед скриптами страницы сервер вставляет слой: `localStorage`/`sessionStorage`
  в памяти (в opaque origin они бросают исключение); `alert`/`confirm`/`prompt`
  — сообщение внутри страницы (без `allow-modals`, который позволил бы
  заблокировать вкладку); отправка формы вызывает обработчики `submit`
  (песочница без `allow-forms` блокирует её до события, `form-action 'none'`
  не даёт ничего отправить); тема приложения из `?theme=` — в `data-theme`
  и `color-scheme`; подгонка высоты, которая останавливается у страниц,
  растянутых на `100vh`. Для страниц модели CSP разрешает `eval` — код в них и
  так произвольный, изоляцию дают песочница и запрет сети. Web Workers и сеть
  недоступны. Проверено в Chromium: анимации (rAF, CSS, SMIL), canvas,
  таймеры, мышь и клавиатура, Web Audio, формы, сообщения, хранилище, тема.
