# ADR-0001: Roadmap как данные в репозитории

- **Статус:** Accepted
- **Дата:** 2026-11-21
- **Элементы roadmap:** TEC-082 (TEC-083 … TEC-087), INF-003

## Контекст

До этого решения план проекта жил в одном `ROADMAP.md`: таблица этапов
спецификации v0.3 и список «Next» без идентификаторов, приоритетов,
зависимостей и критериев приёмки. Таблица состояния этапов дублировалась в
`docs/architecture.md` (§ «Состояние этапов») — две копии одних данных.

ТЗ Functional Expansion (§5, §8) требует: несколько дорожных карт с единым
источником статусов, стабильные идентификаторы, иерархию
Program → Epic → Feature → Task → Subtask, типизированные связи, проверку
целостности, метрики без фиктивного прогресса, удобство работы через Git и
пригодность к автоматической обработке.

## Решение

1. **Данные — TOML в `roadmap/`.** `roadmap.toml` объявляет дорожные карты
   (id, префикс, файл, описание, `hypothesis_driven`) и общий Definition of
   Done; каждая карта — отдельный файл с таблицами `[[item]]`. Новый тип карты
   — новая запись в конфигурации, без изменения кода.
2. **Представления генерируются.** `docs/roadmaps/*.md` и сводный блок в
   `ROADMAP.md` (между маркерами) строит `est-roadmap render`. Элемент
   существует в данных один раз; в других представлениях — ссылкой с текущим
   статусом.
3. **Crate `est-roadmap`** (модель, правила R01–R14, метрики, рендер, CLI)
   входит в workspace, но ни от чего в продукте не зависит и ничем в продукте
   не используется: это инструмент разработки.
4. **Проверка в CI через `cargo test`.** `crates/est-roadmap/tests/repository.rs`
   проверяет данные репозитория, актуальность представлений и соответствие
   JSON Schema коду. Отдельный шаг CI не нужен.
5. **Расположение документов.** ТЗ (§6) предлагает `roadmaps/`,
   `specifications/`, `architecture/`, `decisions/`, `schemas/` в корне.
   Документация проекта уже живёт в `docs/`, поэтому эти каталоги — внутри
   `docs/`; данные — в корневом `roadmap/`, рядом с `ROADMAP.md`. Отдельные
   `architecture/*.md` по подсистемам не созданы: архитектура описана в
   `docs/architecture.md`, а дублирование запрещено (ТЗ §8 п. 8).
   Таблица «Состояние этапов» в `docs/architecture.md` заменена ссылкой на
   сгенерированные представления.

## Рассмотренные альтернативы

- **GitHub Issues / Projects** как источник. Отклонено: данные вне
  репозитория, нет офлайн-проверки целостности и истории в `git log`, сложнее
  связь с путями кода; local-first проекта это противоречит. Синхронизация с
  Issues может появиться позже как экспорт.
- **Markdown с front matter** (по файлу на элемент). Отклонено: сотни мелких
  файлов, ссылки и проверка сложнее, чем у одной таблицы на элемент.
- **YAML/JSON.** TOML уже используется в проекте (манифесты, каталог
  обучения, конфигурация), однозначнее YAML и удобнее JSON для ручного
  редактирования. JSON остаётся форматом экспорта (`est-roadmap export`).
- **Отдельный репозиторий или скрипт на Python.** Отклонено: проект на Rust,
  инструмент проверяется тем же `cargo test`/`clippy`, лишний язык в CI не нужен.

## Последствия

- Изменить план — отредактировать TOML и выполнить `render`; забытый `render`
  или ошибка данных ломают `cargo test`.
- Прогресс без оценок помечается как «unestimated»: владельцу нужно
  проставлять `estimate_days`, чтобы проценты значили больше, чем доля листьев.
- Сроки (`due`) не выдуманы при аудите и пока не заданы; просрочка считается
  командой `metrics` относительно текущей даты, а не в сгенерированных файлах,
  чтобы они не устаревали каждый день.
- Автоматическое сопоставление с состоянием репозитория (TEC-091) и проверка
  записи изменений крупных элементов (TEC-092) — следующие шаги.
